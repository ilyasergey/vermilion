# 2026-08-19 — drop the Veil dependency, move to Lean 4.33.0

Session record for the toolchain migration the user requested: remove the
Veil Lake dependency and take Lean to the newest version Mathlib supports.
Companion facts live in `.claude/memory/foundational-vcgen.md` (the Loom note
this invalidates) and `docs/issues/bit-vector-assert-id-collision.md`.

## 1. What Veil was actually providing

Nothing that any Vermilion module imported. A repository-wide search found no
`import Veil` / `import Loom` anywhere in `lean/`, `examples/`, or
`case-studies/`; the only foreign imports are `import Smt` (two files:
`Vermilion/Obligations.lean` for the ladder's last rung and
`Vermilion/Calibration/Obligations.lean`) and Mathlib.

Veil was a *carrier*: `require veil` pulled `lean-smt` (verse-lab fork, branch
`v4.28.0-for-veil-experimental`) and Loom, and Loom in turn pulled Mathlib
`v4.28.0`. So the dependency was three levels of indirection to obtain two
libraries we use directly, and it pinned the toolchain to 4.28.0 through
Loom's Mathlib pin. The design note about building the future foundational VC
generator on Loom is unaffected in intent, but Loom is no longer in the tree
and must be required directly when that work starts (memory file updated).

## 2. The move

`lakefile.lean` now requires the two real dependencies directly:

- `mathlib` at `v4.33.0` — the newest Mathlib *release* tag (v4.34.0 exists
  only as an rc), which is what fixes the toolchain;
- `smt` at upstream `ufmg-smite/lean-smt` `21aa44ce022f` (its `main` for Lean
  v4.33.0). The verse-lab fork is unnecessary: upstream's `smt` config carries
  both fields the ladder uses (`trust`, `timeout`), verified by reading
  `Smt/Tactic/Smt.lean` before switching.

`lean-toolchain`: `leanprover/lean4:v4.28.0` → `v4.33.0`. Resolved package
set drops veil and Loom entirely (12 packages, all at v4.33.0-compatible
pins); `cvc5` still arrives through `smt`, so the `moreGlobalServerArgs`
plugin wiring and `scripts/lean_env.sh` need no change.

`scripts/run_calibration.py` hard-coded `"lean_toolchain":
"leanprover/lean4:v4.28.0"` in its report JSON; it now reads `lean-toolchain`,
so the calibration report cannot drift from the pin again.

## 3. The one Lean 4.33 behavioural change that mattered

Almost all breakage traced to a single upstream change: **simp no longer
applies a conditional rewrite whose side condition needs a nested rewrite to
discharge.** The discharger proves the condition, but the resulting proof
"fails to assign" (`Simp.Rewrite`'s `.failedAssign`, reachable when
`isDefEq x proof` fails). Minimal reproduction found in this session:

    (Seq.empty.push (7:Int)).index 0 = 7   -- `simp` made no progress

`Seq.index_push_at` requires `i = xs.len`; the discharger rewrites
`Seq.empty.len` to `0` via `len_empty`, proves `0 = 0`, and then the
assignment fails — so indexing into a literal pushed sequence stopped
computing. A related symptom is a *type-incorrect target* after unfolding a
`natClip`/`iteP` chain: rewriting `len` (or `natClip`) underneath an already
built `iteP` desynchronizes the guard proposition from the `Decidable`
instance baked into the term, and `iteP_pos`/`if_pos` stop matching.

Fixes, all library-side (nothing trusted was added; every lemma is ordinary
proved Lean code):

- `Vstd/Seq.lean`: new unconditional if-form `index_push`
  (`@[simp 900] (xs.push x).index i = if i = xs.len then x else xs.index i`),
  which needs no discharge; the targeted conditional lemmas keep higher
  priority so they still fire where their discharge succeeds. `grind =` tags
  on `len_empty`/`len_push`/`index_push_last`/`index_push_at`/
  `index_push_prefix` so the first ladder rung closes these goals via cutsat.
- `Vstd/Seq.lean`: `index_add_right`'s own proof reordered to unfold `len`
  before `index` (the type-incorrect-target case above).
- `Prelude.lean`: two `@[grind =]` remainder-collapse lemmas plus a
  division-guarded `@[simp]` one, for the `((e % 2⁶⁴) % k) % 2⁶⁴` chains Verus
  emits around exact clips. **Deliberately not all `@[simp]`:** as simp
  lemmas they let `simp_all` close goals that committed interactive twins
  expect to survive it (observed breaking sha3 `rho.lean` and
  `theta_inner.lean` during the investigation). The division-form guard is
  provable by omega from linear bounds but not by plain simp, which preserves
  twin behaviour.

## 4. Interactive proofs written (user-directed)

The user's instruction mid-session: make the tests and examples pass, and for
complex case studies that used to verify, close the remaining `sorry`s
interactively. 21 dalek-lite obligations were closed by hand, in four groups:

- `bit_or_is_plus` (u8/u16/u32/u64/u128, 5 VCs): one uniform width-generic
  proof — `x < 2^k → x &&& (y <<< k) = 0` by `Nat.eq_of_testBit_eq`, then
  core's `BitVec.add_eq_or_of_and_eq_zero`. No case split, so u128 costs what
  u8 costs.
- `distribute_over_bit_or` (u8/u16/u32/u64, 8 VCs): these are width-generic
  `BitVec` identities (`ext` + `Bool.and_or_distrib_right`); the range
  hypotheses are not needed at all. The key step is collapsing
  `BitVec.ofInt w ↑((X ||| Y).toNat)` back to `X ||| Y`.
- `or_bit` (2), `mask_or_bound`, `mask_bound_implies_bit_clean`,
  `fe51_limbs_bounded_weaken` (6 VCs): lift the `Bits` Int wrappers to
  `BitVec`, `interval_cases` the small shift amounts, `bv_decide` per branch.
- `add_lemmas.lemma_field_element51_eq_from_limbs_eq` (2 VCs): `Seq.ext`
  plus single-field-structure injectivity — the Seq-extensionality rung the
  ladder still lacks (`docs/issues/seq-extensionality-rung.md`).

`power-of-2`'s committed twin `left_shift_is_pow2` needed the same
`natClip`/`iteP` repair as §3: it now uses the prelude's
`natClip_of_nonneg` directly instead of unfolding to `iteP` and rewriting.

Three read-only sha3 units (`theta_d`, `impl__9_index_mut`,
`impl__10_xor_byte_at`) were healed **without touching their files**, via the
`Prelude.lean` lemmas above; `rho` recovered from `Seq.index_push` alone.
`case-studies/aeneas/` is read-only per standing directive, so library growth
was the only permitted route.

## 5. Editor: vendored sources are navigable (user-requested)

Opening a vendored case-study source (e.g. curve25519-dalek's
`src/lemmas/common_lemmas/bit_lemmas.rs`) was doubly broken:

- **navigation**: the extension assumed one layout,
  `<dir>/generated/<stem>.json` beside `<stem>.rs`. A study that lowers a
  vendored crate keeps every manifest under the study's `generated/` while the
  sources sit inside the gitignored checkout, so nothing resolved. New
  `resolveManifestContext` walks from the file up to the workspace root and
  takes the first manifest that actually mentions it (`manifestCoversRustFile`
  over `rust_file` + each obligation's `rust_span.file`). Verified on real
  data: that file resolves to `case-studies/dalek-lite/generated/bit_lemmas.json`,
  115/115 of whose obligations come from it. Co-located examples still resolve
  on the first hop.
- **spurious red**: because manifests can now span several sources, obligation
  lookup is pinned to the open file (`obligationRecordForFunction` /
  `obligationForContractClause` take an optional `sourceFile`), and — more
  importantly — verify-on-save no longer points the shared driver at a file
  whose artifacts are owned by another directory (`manifestOwnedElsewhere`).
  Such a file is a crate member, not a self-contained program: dalek's driver
  needs the crate root and `--verus-extern subtle=…`, so a standalone run
  would fail and paint that failure on the user's source.
- rust-analyzer is kept out of the vendored trees in `.vscode/settings.json`:
  inside `verus! { … }` those files are not Rust (`proof fn`, `ensures`,
  `#![trigger …]`, `assert(…) by (bit_vector)`), and they belong to crates
  outside this cargo workspace, so it could only report false errors. Full
  IntelliSense there would need verus-analyzer; not wired up.

A third defect surfaced while testing the above: **nothing was painted until a
verification completed in the current session** (`sessionHasResults` gated
`refresh()`), so every file — vendored or not, `simple.rs` included — required
a run before showing anything, and for a file that cannot be run standalone
that meant never. Painting now reads the artifacts on disk, with a staleness
guard: if the source is newer than the check artifact the marks are flagged
stale (withheld, exactly as for a function the user just edited) and the status
line says `edited since it was verified`. Two supporting fixes were needed:
whole-crate judging writes `ga-<manifest>-check.json` with no run status, which
the manifest lookup could not resolve (now resolved through the open files'
manifests); and marks were attributed to `manifest.rust_file` for every
obligation, so a cone-covering manifest put all its marks on the entry point
(now per obligation's own `rust_span.file`).

Macro-generated items needed one more step: `macro_rules!` lemma factories
declare `pub proof fn $name`, which `parseFunctionRanges` cannot match, and the
obligations' spans point at the macro *invocation* — inside no function range.
Those verdicts were silently dropped (shift_lemmas.rs: 1 mark for 757
obligations). Marks now fall back to the obligation's own line, so the file
shows 68 checkmarks, one per generated lemma.

Verified by driving the real `activate()` against the real artifacts through a
stubbed `vscode` module (scratchpad harness, not committed): 68 marks and
`✓ fully verified` for `shift_lemmas.rs` with no run spawned, 1 mark for
`simple.rs` without running it, and both staleness directions. That harness
also exposed a latent crash — `collectDiagnostics` assumed every manifest has
`lean_file` — now guarded.

`collectFunctionMarks` moved to `core.js` (pure, unit-tested) to make this
testable. 6 new unit tests in `editor/vscode-vermilion/test/core.test.js`
(16/16 pass); extension 0.9.7 → 0.9.9; README's VS Code section documents the
behaviour.

## 5b. A false green in the acquisition path, and its blast radius

Investigating why an open dalek twin failed in the editor while the suite
reported the acquisition green uncovered a committed latent defect in
`scripts/run_example.sh`: the whole-crate judging loop invoked
`./target/release/vrml_check`, but only `target/debug` is ever built (the
script's own staleness step, and every other call site, use debug). The
checker exited 127 without producing diagnostics; `--expect-partial`
swallowed the nonzero status; the EMPTY failures file then told `vrml_sync`
"no failures", and sync reclaimed `sorry` placeholders as if automation had
succeeded. Every acquisition sweep on this machine was a no-op reporting
success.

Fixes:
- the call site now uses `target/debug`, and the loop **fails closed on
  infrastructure errors**: a nonzero checker exit with no diagnostics
  aborts the run regardless of `--expect-partial` (which tolerates failed
  OBLIGATIONS, never a failed CHECKER);
- a second ladder defect found in the same investigation: the final `smt`
  rung's "uncapped" interactive default (`smtBudget = 0`) did not rebase
  the heartbeat baseline, so it inherited the declaration's original
  budget — already burned by the twelve earlier rungs — and died before
  cvc5 ever ran. The uncapped branch now rebases and sets
  `maxHeartbeats := 0` (core's real "no limit"), matching its docstring;
- the dalek acquisition was re-run with the working checker to obtain the
  TRUE per-obligation verdicts (results in §7), and the sorry-reclamation
  claims below it re-measured.

Consequence for §4's numbers: the "2,191 sorries reclaimed" figure was
partly an artifact of the false green — the hand proofs and library lemmas
are real and individually kernel-checked, but the machine-attempt
reclamations were unverified until this re-run.

## 8. Follow-ups

- `lean-smt`'s `smt` rung cannot translate goals whose hypotheses contain
  `2 ^ k` (`incorrect number of universe levels NPow.toPow`) or any
  `Vermilion.Seq` term (`incorrect number of universe levels Vermilion.Seq`).
  Pre-normalizing with `norm_num` avoids the pow case but then trips
  `cannot translate a.1` on datatype accessors. Upstream limitation; the rung
  is last on the ladder, so the effect is a missing fallback, not a wrong
  verdict. Worth an issue file.
- `ring` is not in `Vermilion.Obligations`' import closure (`norm_cast`,
  `push_cast`, `linarith`, `nlinarith`, `positivity`, `omega` are). Interactive
  twins currently work around it; consider importing `Mathlib.Tactic.Ring` if
  hand proofs keep needing it, weighed against elaboration cost.
- Remove the `collision_635d62c1` stopgap when the bit-vector assert-id
  collision is fixed at the emitter.
- Loom must be required directly if/when foundational VC generation starts.
